# 探索活动规划器：当前算法困境

本文用于外部算法咨询。项目是一个纯前端、单文件的游戏活动规划器（Cell to Singularity 探索活动），需要根据资源、工厂、升级和前置条件，给出“下一步买什么、什么时候买”的计划。

当前实现的正确性不够稳定：在多个真实存档里，规划器会推荐长时间硬等某个升级，而手工先买一批“不直接产出目标资源”的工厂明显更快。

---

## 1. 产品约束

- 纯前端，最终只有一个 `dist/index.html`。
- 规划在浏览器 Web Worker 中执行，不能阻塞输入。
- 无后端、无外部求解器。
- 典型规模：2～3 种资源、10 个工厂、20～30 个升级、10～20 个前置条件。
- 用户会随时修改资源数量、工厂拥有数、价格、产出和升级状态，计划必须快速重算。
- 支持在线等待和“离线收益”：
  - 在线等待按当前产出线性计算；
  - 离线收益倍率通常 2～4；
  - 离线等待必须取整到完整 3 分钟块（180/360/540… 秒），否则不允许标成离线；
  - 计划里可以混合在线等待和离线段。
- 输出按“当前分段”展示，用户买完这一段后重新规划；不要求一次生成几小时后的完整长链。

---

## 2. 问题定义

状态：

```text
每种资源的当前数量
每个工厂的：已拥有数量、下一台价格、单台产出、价格增长倍率、产出资源、成本资源
每个升级：是否已购买、价格、目标工厂、倍率、前置条件
全局广告倍率
```

一次购买动作：

```text
等待资源到账
→ 买一个工厂（数量 +1，价格 ×增长倍率）
或买一个升级（应用倍率，标记已购买）
```

资源产出：

```text
工厂贡献 = 已拥有数量 × 单台产出 × 全局广告倍率
资源产出 = 基础产出 + 所有工厂贡献
```

规划目标不是固定的“最短时间买某个东西”，而是按当前状态选目标：

1. 有锁定工厂/升级时，反向找最近的可执行前置；
2. 没有锁定时，选一个可执行的新工厂或升级；
3. 当前分段只规划到该目标，买完后重新规划。

## 3. 当前算法实现

代码位置：

```text
src/core/statePlanner.ts
```

### 3.1 目标选择

- `findLockedTarget`：从锁定项反向遍历前置，收集已可执行的前置，选预计等待最短者。
- `findOpenTarget`：没有锁定项时，在可执行工厂/升级中选预计等待最短者。
- 每次只选一个分段目标，`planStateSpace` 只规划到它。

### 3.2 动作闭包

`collectSegmentActions` 从目标花费资源开始：

```text
加入产出目标资源的工厂
→ 加入这些工厂对应的升级
→ 把新工厂/升级的成本资源加入目标资源
→ 重复，最多 8 层
```

目标工厂和目标升级始终保留。

### 3.3 状态搜索

- 每次搜索做两遍：
  1. `directOnly`：只允许直接产出目标资源的工厂；
  2. `fullOnly`：允许完整资源链中的间接工厂；
- 两遍分别搜索，取总时间更短者。
- 使用 A* 优先队列，节点上限 **20,000**。
- 每个配置（工厂拥有数 + 已购买升级）保留少量资源数量 Pareto 前沿。
- 节点保存父指针，目标时回溯生成步骤。
- 每个动作同时尝试两种等待边：
  - 在线精确等待；
  - 3 分钟整数倍离线等待；
  - 搜索选择更短者。

### 3.4 关键过滤

每个候选动作会模拟：

```text
等待时间 + 购买后“目标剩余等待”
```

如果是直接生产目标资源的工厂/升级，只有它让目标剩余总时间严格缩短，才进入搜索。
间接工厂可以绕过这个立即收益检查。

### 3.5 当前参数

```text
MAX_NODES = 20,000
MAX_ACTION_DEPTH = 8
每个工厂最多买到：当前拥有 + 1000 台
```

## 4. 失败案例：肾脏与左心室

### 4.1 存档状态

```text
蓝色：5.24e23，产出 2.96e21/s
红色：4.20e22，产出 2.42e18/s

心脏 243 台
肾脏 1 台
肝脏 0 台

目标：肝脏首台，花费 2.40e24 红色
```

当前计划：

```text
等 2小时48分钟
买左心室 1.20e26 蓝色
再等 3分钟
买肝脏
总时长约 2小时51分钟
```

左心室效果：心脏产出 ×2000。

肾脏：

```text
成本 1.15e21 红色
产出 2.54e20 × 4 = 1.016e21 蓝色/秒
```

当前蓝色总产出只有 2.96e21/s，所以一台肾脏增加约 34% 蓝色产出。

### 4.2 手工先买肾脏的结果

| 开局先买肾脏 | 规划总时长 |
|---:|---:|
| 0 台 | 2小时51分钟 |
| 1 台 | 2小时9分钟 |
| 3 台 | 1小时27分钟 |
| 5 台 | 1小时6分钟 |
| 10 台 | 42分钟 |
| 13 台 | 36分钟 |

13 台大约受红色当前数量限制；规划器一台都没有买。

### 4.3 为什么当前搜索漏掉

肾脏不产目标红色，而是：

```text
花红色
→ 产蓝色
→ 更早买左心室
→ 心脏红色产出 ×2000
→ 更早买肝脏
```

这是两步以上的间接收益。

当前动作过滤只看“这次购买后肝脏剩余等待是否立即缩短”。买肾脏会消耗红色，因此短期让肝脏更晚买到；它在单步评估里被排除。

完整资源链搜索理论上可以走两步，但：

- 动作闭包包含大量工厂/升级；
- 20,000 节点预算很快耗尽；
- A* 启发式用当前产出估算目标等待，忽略了未来工厂/升级带来的产出增长，并不是可采纳启发式；
- 两遍搜索中，直接生产者的“硬等左心室”方案先完成，间接链方案没有在预算内找到。

## 5. 其他失败案例

### 5.1 肌肉与软骨

曾经在目标“软骨”时，规划先等鼻子/耳朵，再在等待结束后买肌肉。手工先买 8 台肌肉后，总时长从 66 分钟降到 48 分钟。

原因相同：肌肉花红色、产蓝色，对目标蓝色的即时收益存在，但搜索预算内先选了另一条路径。

### 5.2 皮肤升级

目标“嘴巴”时，规划没有买“皮下组织”和“真皮层”。两者都放大皮肤产出，皮肤是主要蓝色来源。

手工先买：

- 真皮层：总时长 117 分钟 → 81 分钟；
- 皮下组织：总时长 117 分钟 → 60 分钟。

### 5.3 开局种子补丁的副作用

曾尝试加“开局预购种子”：把所有买得起的目标资源生产工厂先买掉，再递归搜索。

结果：

```text
先买几个大脑
→ 重新规划
→ 又推荐买更多大脑
→ 反复多次
```

因为“买得起”不等于“值得买”。这个种子已经删除，不作为候选方案。

## 6. 当前核心困境

### 6.1 单步收益与多步投资冲突

工厂/升级的收益可能不是立即的：

```text
买 A（花目标资源）
→ 提高资源 B
→ 买 C
→ C 提高目标资源
```

单步“目标剩余等待是否缩短”会拒绝 A。

但如果完全不做这个过滤，所有买得起的工厂/升级都会进入搜索，分支爆炸，20,000 节点内更找不到好方案。

### 6.2 动作数量与搜索预算

当前每个状态可能展开：

- 10 个工厂；
- 20 多个升级；
- 每个动作 1～2 种等待边。

即使只考虑一层，分支已经很大。完整资源链会让动作数进一步增加。

节点上限 20,000 是内存/响应折中；提高到 200,000 会直接 OOM（Node 进程约 4GB）。

### 6.3 启发式不可采纳

当前启发式大致是：

```text
目标剩余花费 ÷ 当前目标资源产出
```

它假设未来产出不变。实际上买工厂/升级会提高产出，所以它可能高估剩余时间，不是可采纳 A* 启发式，可能先返回较差目标路径。

### 6.4 批量购买

用户见过一次回头买 800 台工厂的情况。当前搜索是“每次买 1 台”：

- 100～200 台需要 100～200 层状态；
- 搜索深度和节点数都很大；
- 不能把“买 13 台肾脏”当成一个批量动作评估。

当前只有 `+1000` 的硬上限，没有批量动作。

### 6.5 目标选择本身是贪心的

当前目标选择只看“预计等待最短”：

- 目标可能是“肝脏”；
- 更优策略却是先买“肾脏”和“左心室”；
- 目标选择没有把“买目标前的投资组合”纳入评估。

### 6.6 在线/离线边混合

每个动作都可以选择在线等待或离线 3 分钟块。离线块取整会改变最优投资数量，使问题不再是简单的连续时间最短路。

## 7. 已尝试但不够好的方案

| 方案 | 问题 |
|---|---|
| 开局预购种子 | 买一堆大脑，反复推荐，已删除 |
| 单步收益阈值 0.1%/1 秒 | 会排除需要连续买 100～200 台的早期工厂，已删除 |
| 只允许直接生产者 | 漏掉跨资源链，不可用 |
| 完整闭包 + 20k A* | 分支太大，仍漏掉肾脏/左心室链 |
| 提高节点到 200k | OOM |
| 两遍 direct/full 搜索 | 直接方案先完成，间接链仍找不到 |
| 种子递归 | 反复购买低价值工厂，用户明确反对 |

## 8. 希望咨询的问题

1. 这类“购买会改变未来产出、目标是一系列购买”的问题，适合用哪类算法？
   - Beam search？
   - MCTS？
   - 动态规划/整数规划？
   - 分层规划（先决定投资组合，再排时间）？
   - 其他？

2. 如何表示“买 k 台工厂”的批量动作，避免 100～200 层单台展开？
   - 固定批量候选（1/5/10/25/50/100/200）？
   - 连续化后取整？
   - 对每个工厂求最优购买数量？

3. 如何在有限时间内评估“先买 A 再买 B”的间接收益？
   - 多步 lookahead？
   - 对目标依赖图做动态规划？
   - 只对少量关键资源/工厂做组合枚举？

4. 目标选择应该继续贪心，还是把“目标 + 投资组合”一起搜索？
   - 如果一起搜索，如何避免状态爆炸？
   - 是否应该固定“下一个门禁”，只在门禁内优化？

5. A* 启发式如何变得可采纳？
   - 用最大可能产出做下界？
   - 用资源依赖图的最短等待做下界？
   - 放弃 A*，改用 Dijkstra/beam？

6. 在线等待和 3 分钟离线块混合时，有没有成熟的离散化建模方式？

---

## 9. 评估标准

一个候选算法至少要满足：

- 对本文肾脏案例，能找到“先买若干肾脏，再买左心室/肝脏”的方案；
- 对肌肉/皮肤案例，能找到先买工厂或皮肤升级的方案；
- 不反复推荐“买几个大脑”这种微小收益动作；
- 单次规划在浏览器 Worker 中最好 1 秒内完成，最多几秒；
- 内存不能超过普通浏览器标签页可承受范围；
- 输出必须是用户可执行的购买步骤，而不是抽象策略。
